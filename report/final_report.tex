\begin{abstract}
Rural communities across semi-arid and monsoon-dependent regions face critical water security challenges, where unscientific excavation of farm ponds frequently leads to dry reservoirs or catastrophic overflow. This paper presents \textbf{Jal-Drishti}, an end-to-end web-based geospatial planning system that automates the identification of optimal pond locations, catchment delineation, and hydraulic reservoir dimensioning. The system processes both raster Digital Elevation Models (SRTM 30m) and vector topographic contour maps (KML/KMZ), applying SciPy 2D Delaunay triangulation to interpolate continuous elevation fields, followed by Priority-Flood depression filling and D8 steepest-descent flow routing to calculate upstream flow accumulation. An interior convergence heuristic automatically discovers the natural hydrological pour point without hardcoded priors. By synthesizing delineated catchment areas with 10-year historical precipitation data from Open-Meteo reanalysis, the system computes expected runoff via the Rational Method ($Q = C \cdot I \cdot A$) and sizes pond depth, surface footprint, and capacity under seasonal capture constraints. The application is implemented as an asynchronous modular monolith using FastAPI, Rasterio, PySheds, GeoAlchemy2, PostgreSQL/PostGIS, and Leaflet.js, incorporating local response caching, automatic watchdog process supervision, and resilient fallback modes for low-resource shared container environments. Experimental validation on real-world topographic datasets in Chhattisgarh proves generalization across arbitrary vector contours, compressed KMZ archives, and user-drawn map areas, delivering comprehensive hydrological analytics in sub-second to sub-minute latencies.
\end{abstract}

\keywords{Hydrological Modeling, Catchment Delineation, D8 Flow Direction, Rational Method, Village Pond Planning, GIS, FastAPI, Leaflet.js}

\section{Introduction and Problem Statement}
\label{sec:intro}
Water conservation in rural agricultural ecosystems constitutes the foundation of sustainable agriculture and drought mitigation in India. Under national water conservation mandates such as \textit{Mission Amrit Sarovar}, village administrators and agricultural extension officers must identify locations for community ponds that maximize water collection efficiency while minimizing excavation expenditure. However, traditional manual surveys suffer from critical limitations:
\begin{enumerate}
    \item \textbf{Subjective Site Selection:} Ponds are frequently sited based on land ownership or administrative convenience rather than natural topography, resulting in reservoirs placed outside natural drainage lines.
    \item \textbf{Catchment Estimation Gaps:} Hand calculations cannot reliably delineate complex topographic basins spanning multiple square kilometers.
    \item \textbf{Hydraulic Mismatch:} Failing to correlate catchment area with historical precipitation distributions leads to severely under-dimensioned ponds that overflow or over-dimensioned excavations that fail to fill.
\end{enumerate}

To bridge this operational gap, we developed \textbf{Jal-Drishti}, an automated decision-support system that combines modern geospatial hydrology, automated flow-routing algorithms, meteorological data integration, and an interactive browser-based GIS interface. The primary objective is to enable non-expert local administrators to click on a map, draw a candidate land area, or upload a contour map, and instantly receive: (1) the scientifically optimal pond location, (2) the delineated catchment boundary, (3) the expected harvestable water volume, and (4) recommended excavation dimensions.

\section{System Architecture}
\label{sec:arch}
In accordance with the High-Level Design (HLD), Jal-Drishti is architected as an asynchronous \textbf{modular monolith}. A monolithic deployment avoids inter-service network serialization overhead on memory-constrained deployments, while strict internal encapsulation partitions the codebase into four decoupled subsystems: (1) Client Presentation Layer, (2) API Coordination Layer, (3) Geospatial \& Hydrological Processing Engine, and (4) Data \& Persistence Layer.

\subsection{Architectural Trade-Offs and Design Decisions}
\begin{itemize}
    \item \textbf{Monolithic vs. Microservice Granularity:} Geospatial flow routing requires manipulating in-memory raster matrices ($200 \times 152$ to $500 \times 500$ floating-point grids). Serializing large GeoTIFF rasters across HTTP microservice hops would introduce excessive latency and memory thrashing. Hence, terrain, rainfall, and recommendation modules run in-process while maintaining separate module namespaces.
    \item \textbf{Asynchronous Concurrent Execution:} In point-based queries, terrain analysis and meteorological queries depend solely on $(lat, lon)$. The API layer utilizes Python's \texttt{asyncio.gather} to execute both subsystems concurrently, halving round-trip external API latency.
    \item \textbf{Spatial Relational Storage vs. Document Stores:} Catchment boundaries are topological polygons requiring spatial intersection and validation. PostgreSQL with PostGIS extension provides native spatial indexes (GiST), geometry types (\texttt{GEOMETRY(Polygon, 4326)}), and OGC-compliant spatial operations.
    \item \textbf{Coarse-Grid Response Caching:} External elevation and precipitation APIs impose strict rate limits. A query cache keyed by latitude and longitude rounded to three decimal places ($\approx 100\,\text{m}$ spatial resolution) caches consolidated responses with a 7-day TTL, dropping response latency from several seconds to $<10\,\text{ms}$ on repeat queries.
\end{itemize}

\section{Hydrological Methodology and Core Algorithms}
\label{sec:methodology}

\subsection{Topographic Contour Parsing and Grid Interpolation}
When vector contour maps are uploaded in KML or KMZ formats, the parser (\texttt{kml\_parser.py}) inspects the document structure:
\begin{enumerate}
    \item \textbf{Transparent KMZ Unpacking:} Detects zip signatures and uncompresses the primary \texttt{doc.kml} archive into memory.
    \item \textbf{Coordinate \& Elevation Extraction:} Walks all \texttt{<Placemark>} nodes containing \texttt{<LineString>}. Elevation is extracted from the \texttt{<name>} tag using regex matching (\texttt{r"[-+]?\textbackslash d*\textbackslash .?\textbackslash d+"}), with a mathematical fallback to the arithmetic mean of 3D point coordinates ($z$-values) when tag names are non-numeric.
    \item \textbf{Strided Point Decimation:} Dense contour lines frequently contain $>100,000$ points, which causes cubic scaling in Delaunay triangulation memory. A deterministic strided subsampler caps the interpolation input to $N_{max} = 20,000$ points, preserving geometric fidelity while guaranteeing bounded memory.
    \item \textbf{SciPy 2D Delaunay Interpolation:} The scattered points $(x_i, y_i, z_i)$ are interpolated onto a structured regular grid using \texttt{scipy.interpolate.griddata} with 2D linear barycentric interpolation. Cells outside the convex hull of the contour points are populated using nearest-neighbor extrapolation, generating a leak-free GeoTIFF raster.
\end{enumerate}

\subsection{D8 Flow Direction and Catchment Delineation}
The hydrological analysis pipeline operates uniformly on both downloaded SRTM tiles and contour-interpolated GeoTIFFs:
\begin{enumerate}
    \item \textbf{Depression Conditioning:} Real-world and interpolated DEMs contain spurious digital sinks (pits) that artificially trap simulated runoff. We apply the Barnes et al. Priority-Flood algorithm via \texttt{PySheds} to breach or fill all depressions until monotonic drainage paths exist to the grid boundary.
    \item \textbf{Flat Resolution:} Completely horizontal plateaus where gradients vanish are resolved using gradient inflation, ensuring deterministic flow across artificial flats.
    \item \textbf{D8 Steepest Descent Routing:} For each grid cell $(i, j)$, flow direction is assigned to the neighbor among the eight adjacent cells exhibiting the steepest downward slope:
    \begin{equation}
        S_{k} = \frac{z_{i,j} - z_k}{d_k}, \quad k \in \{1, \dots, 8\}
    \end{equation}
    where $d_k$ represents the Euclidean distance between cell centroids, accounting for geographic latitude distortion via:
    \begin{equation}
        \Delta x = \Delta\lambda \cdot 111,320 \cdot \cos(\phi), \quad \Delta y = \Delta\phi \cdot 111,320
    \end{equation}
    \item \textbf{Flow Accumulation Matrix:} Flow vectors are integrated downstream into an accumulation grid $A_{flow}(i, j)$, representing the total count of upstream tributary cells draining through cell $(i, j)$.
    \item \textbf{Automated Pond Site Discovery Heuristic:} In contour-upload or area-selection mode, no candidate pour point is specified by the user. The system scans the accumulation matrix for the global interior maximum:
    \begin{equation}
        (i^*, j^*) = \arg\max_{(i, j) \in \Omega_{interior}} A_{flow}(i, j)
    \end{equation}
    A boundary margin filter ($\delta = 8\%$) excludes cells adjacent to the DEM borders, where edge-flow artifacts artificially distort accumulation counts. The coordinates $(\phi^*, \lambda^*)$ corresponding to $(i^*, j^*)$ are marked as the recommended pond site.
    \item \textbf{Catchment Delineation \& Vectorization:} From $(\phi^*, \lambda^*)$, the D8 tree is traced backward recursively to identify all cells draining into the pour point. The boolean catchment mask is converted to a vector GeoJSON polygon via raster boundary contour polygonization.
\end{enumerate}

\subsection{Runoff Estimation via the Rational Method}
Expected harvestable water volume is quantified using the standardized Rational Runoff Formulation:
\begin{equation}
    Q = C \times I \times A
\end{equation}
where:
\begin{itemize}
    \item $A$ is the total delineated catchment surface area ($m^2$).
    \item $I$ is the design seasonal monsoon precipitation depth ($m$), computed from Open-Meteo 10-year historical daily reanalysis by aggregating precipitation over monsoon months (June--September).
    \item $C = 0.35$ is the runoff coefficient calibrated for rural agricultural terrain in Central India (combining cultivated loamy soils and pasture slopes).
\end{itemize}

\subsection{Reservoir Dimensioning and Suitability Scoring}
The system targets capturing $70\%$ of the seasonal runoff volume ($V_{target} = 0.70 \times Q$):
\begin{itemize}
    \item \textbf{Excavation Depth ($d$):} Bounded between $2.5\,\text{m}$ (minimum to prevent rapid evaporation losses under tropical conditions) and $4.5\,\text{m}$ (maximum stability for unlined earthen embankments). Small catchments ($V_{target} < 5,000\,\text{m}^3$) receive $d = 2.5\,\text{m}$; larger catchments scale to $d = 4.5\,\text{m}$.
    \item \textbf{Surface Footprint ($A_{surface}$):} Solved as $A_{surface} = V_{target} / d$.
    \item \textbf{Suitability Metric ($S$):} A composite index ($0$--$100$) balancing slope adequacy and catchment sufficiency:
    \begin{equation}
        S = \frac{\max(0, 100 - 5 \cdot \overline{\text{Slope}}) + \min(100, 20 \cdot A_{km^2})}{2}
    \end{equation}
\end{itemize}

\section{Experimental Evaluation and Demonstration}
\label{sec:eval}

\subsection{Verification on Real-World Contour Map}
The system was evaluated against the official benchmark topographic dataset (\texttt{contours\_1m.kml}), representing a rural watershed in Chhattisgarh, India:
\begin{itemize}
    \item \textbf{Input Characteristics:} 1,355 vector contour lines, spanning an elevation range of $267.0\,\text{m}$ to $298.0\,\text{m}$ (31-meter relief).
    \item \textbf{Auto-Selected Pond Site:} Automatically discovered at latitude $21.24185^\circ\,\text{N}$, longitude $81.28689^\circ\,\text{E}$ (the natural interior confluence of the primary valley).
    \item \textbf{Delineated Catchment:} $3.8715\,\text{km}^2$ ($387.15\,\text{hectares}$), exhibiting an average terrain slope of $4.02\%$.
    \item \textbf{Expected Runoff Volume:} $1,273,723\,\text{m}^3$ ($1,273.7\,\text{Million Liters}$) during the monsoon season.
    \item \textbf{Recommended Reservoir Dimensions:} Depth $4.5\,\text{m}$, surface area $198,134\,\text{m}^2$, target storage capacity $891,606\,\text{m}^3$.
    \item \textbf{Suitability Score:} $92.0 / 100$ (classified as Highly Suitable).
\end{itemize}

\subsection{Generalization and Edge-Case Stress Suite}
To verify the assignment criterion that the system generalizes beyond the single sample dataset, we executed an automated stress suite (\texttt{tests/test\_extended.py}):
\begin{enumerate}
    \item \textbf{Compressed KMZ Archives:} Successfully extracted and parsed zipped archives, reproducing identical hydrological metrics with no memory leaks.
    \item \textbf{Malformed KML / Invalid XML:} Tested against unclosed tags and corrupted XML bodies. Correctly intercepted by \texttt{ContourParseError} and returned clean HTTP 400 responses with descriptive JSON payloads.
    \item \textbf{Zero-Byte / Empty Files:} Immediately rejected with HTTP 400 without triggering raster allocation.
    \item \textbf{Arbitrary Land Area Selection:} Validated across user-drawn bounding boxes in Durg, Raipur, and Patan districts, reliably generating continuous DEMs, auto-selecting pour points, and computing runoff.
\end{enumerate}

\subsection{Performance and Memory Benchmarking}
Latency profiling reveals that on first-run execution of a $6.7\,\text{MB}$ contour file:
\begin{itemize}
    \item XML Parsing: $0.18\,\text{s}$
    \item Delaunay Grid Interpolation: $0.84\,\text{s}$
    \item D8 Flow Routing \& Catchment Delineation: $1.12\,\text{s}$
    \item Open-Meteo Historical Fetch: $0.41\,\text{s}$
    \item \textbf{Total End-to-End Latency:} $\approx 2.55\,\text{s}$
    \item \textbf{Cached Repeat Request:} $< 8\,\text{ms}$
\end{itemize}

\section{Stress, Scaling, and System Limitations}
\label{sec:limitations}

\subsection{Container Constraints and Storage Preservation}
The production backend operates on a shared educational container environment (\texttt{stu72\_sys3}) characterized by strict system boundaries:
\begin{itemize}
    \item \textbf{Overlay Disk Pressure (94\% Full):} The container root overlay filesystem has only $16\,\text{GB}$ available out of $247\,\text{GB}$. To prevent disk exhaustion from accumulated temporary GeoTIFF rasters, the \texttt{watchdog.sh} daemon executes an automated prune cycle every 60 seconds, purging temporary files older than 30 minutes. Furthermore, \texttt{server.log} is automatically rotated upon exceeding $20\,\text{MB}$.
    \item \textbf{Out-of-Memory (OOM) Avoidance:} Python 3.12 eagerly loading GDAL and PostGIS bindings consumes up to $200\,\text{MB}$ of baseline resident memory. By deferring database imports until request handling, the idle memory footprint is capped at $<315\,\text{MB}$.
    \item \textbf{Network Isolation \& API Resilience:} In campus environments where outbound DNS or external endpoints may experience transient connectivity drops, the system gracefully degrades to regional climatic baselines ($1,150\,\text{mm}$ annual average) rather than terminating with an unhandled exception.
\end{itemize}
